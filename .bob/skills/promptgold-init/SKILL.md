# Promptgold Init

Follow these steps in order. Do not skip ahead — each step gates the next.

## Step 1 — Read the source files

Read both files the user specifies:
- The **system prompt** (any text file).
- The **policy document** (Markdown or PDF).

Use `read_file` for text files. For PDFs use `office_read` with `mode: text`.
If either path is ambiguous, ask with `ask_followup_question` before reading.

## Step 2 — Extract and table every testable rule

Scan both files for every testable rule. A rule is testable when it contains:
- a **must** / **always** / **never** / **do not** directive,
- an exact string, phrase, or forbidden topic,
- a numeric limit (character count, word count, number of items, dollar amount, timeframe).

Build a Markdown table with three columns:

| Rule | Source line | Test type |

- **Rule**: one-sentence description of what the model must or must not do.
- **Source line**: file name + line number (e.g. `system_prompt.txt:12`).
- **Test type**: one of `contains`, `matches`, `judge`.

**Assign test type using this decision tree (strictly in order):**
1. If the rule demands an exact string or forbidden substring → `contains`
2. If the rule demands a number, currency, date pattern, or regex-matchable format → `matches`
3. Only if neither 1 nor 2 applies (the rule is about tone, meaning, or intent) → `judge`

For every `judge` row add a fourth column **Reason** explaining in one line why `contains`/`matches` cannot cover it.

**Show the completed table to the user and wait for confirmation before writing any test code.**
Ask: "Does this rule list look complete? Any rules to add, remove, or change test type for?"
Incorporate any feedback, then proceed to Step 3.

## Step 3 — Prepare the test file path

Derive the app name from the system-prompt file's parent directory name (e.g. `examples/supportbot/system_prompt.txt` → app name `supportbot`).
The output file is `examples/<app>/test_generated.py`.

Before writing, read `examples/supportbot/test_bot.py` to confirm current style conventions (imports, MODEL constant, `@prompt_test` decorator).
Also read `.bob/skills/promptgold-init/template.py` for one ready-made example of each assertion type.

## Step 4 — Write the tests

Write `examples/<app>/test_generated.py` using `write_file`.

**Hard rules (from project rules — never violate):**
- Import line: `from promptgold import contains, judge, matches, prompt_test`
- Add adversarial imports only when the policy doc specifically asks for jailbreak / injection / leak tests:
  `from promptgold.adversarial import injections, jailbreaks, leak_probes`
- Decorate every test with `@prompt_test(model=MODEL)`.
- Function names: `test_<rule_slug>` — lowercase, underscores, no spaces.
- One test per rule; one rule per test.
- Prefer `contains()` and `matches()` over `judge()` (mirror the table from Step 2).
- When using `judge()`, the judge model must differ from the model under test. Add a comment:
  `# judge: set PROMPTGOLD_JUDGE_MODEL to a different model before running`
- Never call pytest with `--bless` or `--no-cassette`.
- Never edit `.promptgold/golden/*.json`.

**File structure to follow:**
```python
"""promptgold tests for <AppName> — auto-generated by promptgold-init.

Run:
    pytest examples/<app>/          # replay cassettes, catch regressions
"""

import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).parent))

from <app_module> import chat  # noqa: E402

from promptgold import contains, judge, matches, prompt_test  # noqa: E402

MODEL = "openai:gpt-4o-mini"


@prompt_test(model=MODEL)
def test_<rule_slug>(llm):
    reply = chat(llm, "<probe question that triggers the rule>")
    assert <assertion>
```

## Step 5 — Run the tests

Run pytest with the venv binary — no `--bless`, no `--no-cassette`:

```
./.venv/bin/pytest examples/<app>/test_generated.py -v
```

Use `execute_command`. Report the full result: passed, failed, error counts, and any tracebacks.
If cassettes are missing and pytest complains, stop and ask the user whether to record them
(they must run `--bless` themselves).

## Step 6 — Coverage check

After the run, produce a **coverage summary** table:

| Policy rule | Test function | Status |
|---|---|---|
| ... | `test_<slug>` | covered |
| ... | — | no test — *reason* |

Explain any gap: rule was untestable (open-ended, subjective with no objective proxy), excluded by
user in Step 2, or missed accidentally (fix it).

## Step 7 — Task summary

End with:
- **Tests added**: N
- **Attacks run**: list adversarial test names or "none"
- **Failures found**: N (list test names)
- **Fixes proposed**: describe any prompt changes suggested to make failing tests pass
- **Cost**: paste the run's cost line from the pytest summary if present
